建议采用“4yue 源码标准库 + C Runtime + 少量编译器内建”的三层结构。不要把所有标准库功能硬编码进 Codegen。

## 推荐结构

```text
std/
├── prelude.tp       # 默认加载：min、max、abs 等
├── math.tp
├── io.tp
└── string.tp

runtime/
├── include/
│   └── 4yue_runtime.h
└── src/
    ├── io.c
    ├── memory.c
    └── string.c
```

三层职责：

- `std/*.tp`：使用 4yue 编写的普通函数，例如整数计算。
- `runtime/*.c`：文件、终端、内存、字符串等需要操作系统支持的功能。
- 编译器内建：`sizeof`、类型转换等无法表示为普通函数的操作。

## 实施顺序

1. **先实现自动加载 `std/prelude.tp`**

   当前 [main.c](/Users/nano/Projects/tap-lang/4yue/src/main.c:118) 只解析一个文件。可以分别解析 `std/prelude.tp` 和用户源码，然后合并两个 `ProgramNode.functions` 链表。

   不建议直接拼接源码文本，否则错误信息中的文件名和行号会混乱。

2. **增加模块导入语法（已实现）**

   当前支持点分隔模块名、名称空间、`as` 别名、递归加载，以及重复和循环导入去重。
   具体规则见[模块导入文档](module.md)。

3. **增加外部函数声明（已实现）**

   Runtime 需要一种声明方式，例如：

   ```text
   extern fn rt_print_i64(value: i64): i32;
   ```

   AST 的 `FunctionNode` 可以增加 `is_extern`。Codegen 对外部函数只生成 LLVM 声明，不生成函数体。

4. **建立稳定 ABI**

   建议运行时符号统一加前缀：

   ```text
   __4yue_print_i64
   __4yue_alloc
   __4yue_string_concat
   ```

   同时明确：

   - 每种整数类型的 C 对应类型
   - 字符串内存布局
   - 谁负责释放内存
   - 错误码和空指针规则

5. **链接 Runtime**

   当前 [codegen.c](/Users/nano/Projects/tap-lang/4yue/src/codegen.c:646) 直接调用 `ld`。加入 Runtime 后，建议改用 `clang` 或 `gcc` 驱动链接：

   ```bash
   clang program.o lib4yue_runtime.a -o program
   ```

   这样 C Runtime、系统库和平台启动文件更容易正确链接。

6. **兼容 `-run-lli`**

   `lli` 运行时需要加载 Runtime 动态库，例如：

   ```bash
   lli --load=lib4yue_runtime.dylib output.ll
   ```

   Linux 对应 `.so`。另一种方式是把 Runtime 编译成 LLVM bitcode，再与用户模块链接。

## 建议的第一个版本

第一阶段只做：

- 自动加载 `std/prelude.tp`
- 提供 `min`、`max`、`abs`
- 检测重复函数
- 增加标准库运行测试

第二阶段已实现 `extern fn` 和基础 C Runtime，当前提供按键、休眠、清屏和随机数能力。
后续输入输出、内存与字符串也应沿用同一 Runtime ABI。
